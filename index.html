What changed, and what it means for a demonstration

A paper can now only be assembled from approved questions. The 56 questions that were sitting in the bank had never been reviewed by anybody — nothing in the platform could approve them — so the chair has to work through them before a new paper can be built. The paper already released is unaffected.

The chair cannot approve a question they wrote themselves. That is refused on the screen, refused by the service, and refused by the database, because “somebody checked this” being satisfiable by one person twice is the thing the step exists to prevent.

Proctor sign-in works again — fixed 11 September

Until 11 September every proctor was refused with “Those credentials are not valid”, even with the right password. It was the sign-in page, not the accounts. To sign in now:

  1. Reload the page once with Ctrl+Shift+R (Mac: Cmd+Shift+R) so the browser takes the new version.
  2. Use /staff/sign-in — not the admin sign-in, which refuses proctors.
  3. Email and password, then the 6-digit code from the authenticator app.
  4. If it is refused, check the password and stop after two tries: five failures lock the account for up to 15 minutes, and every retry during the lock extends it.

Making a paper

Six steps across two roles. Sign in at /admin/sign-in for all of them. The order matters: a set cannot be assembled before questions exist, and cannot be released until two different controllers have signed it.

Create the exam no screen yet
controller
The API exists and is correctly scoped, but nothing in the interface calls it — today an exam is created by running seed-exam.mjs. This is the only step in the chain with no front door.
Allocate outcomes to setters
controller · /faculty/allocation
Tell a named setter to write N questions for a course outcome by a date. Progress is counted from questions that actually exist, not from a status somebody remembers to update.
Author the questions
faculty · /faculty/question-new · /faculty/question-bank
Fifteen question types. A setter reads back only their own questions.
Or generate them from source material
faculty · /faculty/question-generate
Drafts land in the same question bank and follow the same approval path. The generator requires the same signed permission as writing one by hand.
Assemble a set
controller · /faculty/sets
The assembler chooses against a blueprint and sees question attributes only — no stem, no options, no marking key. Sets are encrypted at rest.
Two controllers sign, then release
controller ×2 · /controller/paper-release
Sign in as the first controller and sign; sign out; sign in as the second and sign. One person cannot do both — refused at the interface, at the API, and by an append-only trigger in the database.

Before you experiment

Only one set may be released per exam — a second released set breaks paper serving. Exam 1 already has one. To exercise the flow, create a fresh exam rather than assembling a second set against the live one.

Admissions

Invite-only, by design: a public form on an exam platform collects applications from anyone, which means duplicate identities and a moderation queue nobody is staffed to run.

Add the candidate and send the link
command · /command/admissions
A single-use link is emailed. Only its hash is stored, so a database backup contains no working links.
The candidate applies
public · /apply/<token>
Four steps: details, a photograph of their ID, a live photograph of their face with head turns, then send. Both photo steps offer the camera and a file, because a laptop browser ignores the camera hint a phone honours.
A person approves it
command · /command/admissions/<id>
The device's face-match score is recorded and shown, and decides nothing — every approval names a human. Approval, roster hand-off and email are reported separately, so a bounced email never un-approves anybody.

Email

Sent through Brevo over SMTP, from code-support@collegeranger.com, which forwards to a real inbox so replies reach a person. Proved by the headers of a delivered message, not by a log line: 

Authentication-Results: mx.google.com;
   dkim=pass  header.i=@collegeranger.com header.s=brevo2
   spf=pass   smtp.mailfrom=bounces-…@mail.collegeranger.com
   dmarc=pass header.from=collegeranger.com
  • SPF is aligned to collegeranger.com, not to Brevo, because the branded sending subdomain is mail.
  • The branded subdomain must never be exams — that name is the live site's own record, and a tracking CNAME there would take the platform offline.
  • Link tracking is switched off in code (Brevo transactional settings). Brevo rewrites links through a host whose certificate is issued for a different domain and expired, which met candidates with a browser security warning.
  • Namecheap appends the domain to whatever you type: the host field takes mail, never mail.collegeranger.com.

Fixed since the bug sheet

Thirteen testers filed against the 9–10 September round. Most of the sheet came down to two causes.

ReportedWhat it actually was
Proctor logins “not valid” — Ahmedabad and Lucknow (11 Sep) The passwords were right. The proctor sign-in page was telling the server it was the admin door, and the admin door refuses proctors with the same words as a wrong password. Fixed and checked on the live site for both accounts. Reload the page once; see Proctors — the hall. fixed
Study Material, Candidate Registry and PDF upload all returning 502 Bad Gateway One process. The service behind every /agent/* screen had no startup entry on this machine, so it had never run once, and its libraries were never installed. Seven people reported it as three different bugs. fixed
“Logged out at every step”, “logs out on refresh” Not a fault. Signing in ends any other session on the same account, and thirteen people were sharing six logins — 171 sessions ended that way in six hours. Everyone now has their own account. fixed
Sign out lands on the student login page Staff were being returned to the candidate door, which asks for an enrollment number they do not have. fixed
Search, notifications and help do nothing Correct — they were buttons with nothing behind them, and the notification dot showed unread items for a feature that does not exist. Removed until they are real. fixed
Phone accepts more than 10 digits; date of birth accepts future dates Both true. Mobile is now exactly ten digits in an Indian series; date of birth must fall between 10 and 100 years ago. fixed
Developer text on screen (“qbank · GET /questions”) Thirteen internal notes were rendering on production screens, including one describing how the paper-release page fetches its data. fixed
— not reported, found while fixing — The admin door accepted a proctor’s correct password and only then refused the role, so anyone could confirm a staff password was valid without the second factor. Now indistinguishable from a wrong password. fixed
OTP never arrives True and still true: no SMS provider is connected. Use the tester code above, or choose Email on the forgotten-password screen, which does send. worked around

Do not

  • Do not let a second controller sign a test set. Two released sets for one exam breaks paper serving.
  • Do not enable the walkthrough account on the server. It can assume every role in turn; it is unreachable there by construction and must stay so.
  • Do not weaken a separation rule to make something pass. If that seems necessary, the approach is wrong.
  • Do not renumber the two migrations that share number 0020. Both are applied; the next free number is 0024.
  • Do not report face match, liveness or room scan as tested. They have only ever run against a synthetic camera.
